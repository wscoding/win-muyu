# 可扩展功能与接口分析

> 结论先行：**接口 v3 已经把「不发版就能改行为」的骨架搭好了**——
> 运行时配置、公告、资源包清单、版本发布、功德语都不需要改代码。
> 真正值得投入的下一步是**账号体系**（一次改动解锁跨设备同步、会员、战绩继承），
> 以及客户端侧的三个页面（功德榜 / 每日一签 / 云同步设置）。
> 本文按「值不值得做」排序，并标注每项需要动什么。

## 2. 改代码就能加、**不需要动表**的扩展

数据表已经覆盖这些场景，接线即可。

### 2.1 客户端：功德榜页面 ★ 推荐先做

服务端 `Rank::leaderboard()` 已支持 `day / week / month / all` 四个口径并按
`daily_active` 聚合，`/profile` 也已返回称号、连续打卡、本周敲击、名次。

要做的事：
- 客户端新增 `ui/pages/leaderboard_page.dart`（用 `PanelScaffold`），
  调 `/leaderboard?range=week` 与 `/profile?device_id=`；
- 在设置页加一个开关调用 `TelemetryService` 新增的 `optIn` 方法
  （`POST /profile/opt-in`，需要昵称）。
- 服务端侧**零改动**。

价值：这是唯一能让用户主动打开 App 的社交功能，也是「敲击 → 反馈」闭环里
最能提升留存的一环。成本：客户端一个页面 + 一个开关。

### 2.2 客户端：每日一签 + 公告展示

`/blessing`（同一天结果稳定、次日自动轮换）与 `/announcement` 都已可用，
`TelemetryService.fetchBlessing()` 也已实现。

要做的事：在悬浮窗或菜单顶部加一行「今日一签」，公告按 `level`
（info / notice / warn）决定展示样式。

价值：低成本提升「仪式感」，且文案在后台随时可改。

### 2.3 客户端：设置云同步的开关

`TelemetryService.pushSettings/pullSettings` 已实现，服务端白名单里有 18 个键
（音量、音效包、皮肤、快捷键、窗口位置、透明度、语言、开机自启……）。

要做的事：设置页加一个「同步到云端 / 从云端恢复」，处理 409 冲突
（服务端会把云端版本一起返回，让用户选合并还是覆盖）。

价值：换机器不用重配，是这个工具类应用最实用的功能之一。
**注意**：目前同步粒度是「设备」，换机器等于换命名空间 ——
真正的跨设备同步需要 2.6 的账号体系。

### 2.4 皮肤 / 音效包真正落地

`asset_packages` 表与 `/assets` 接口都已就绪，但没有内容，也没有文件托管。

要做的事：
1. 在服务器上开一个资源目录（或托管到对象存储）；
2. 后台「内容与配置 → 资源包」录入条目（下载地址、体积、SHA-256）；
3. 客户端实现「下载 → 校验 SHA-256 → 解包到应用目录 → 应用」。

价值：可以做内容生态（用户自制皮肤），也天然是未来的付费点。
成本主要在客户端的下载与校验逻辑。

### 2.5 崩溃上报真正接上客户端

`TelemetryService.reportCrash()` 已实现，但**还没有在任何地方被调用**。

要做的事：在 `FlutterError.onError` 与 `PlatformDispatcher.instance.onError`
里调一次。服务端已做同设备同错误 10 分钟去重，不会刷爆表。

价值：移动端/桌面端线上问题的唯一可见窗口，成本极低。

### 2.6 小时级热力图

现在刻意**不写** `hourly_stats`：这台机器只有 4G 内存、binlog 全开，
每次敲击上报再多一次 upsert 不划算。

要做的事：新增 `hourly_stats(stat_date, hour, app_id, taps)`，
客户端在 `/taps/batch` 里带上每个小时的增量数组（需要客户端本地按小时聚合）。

价值：看板能展示「什么时段敲得最多」，很出效果。
建议等写入量稳定后再做，或者只对「天级活跃设备」抽样统计。

## 3. 需要新增表 / 较大改造的扩展

### 3.1 账号体系 ★ 最高杠杆

这是**一次改动解锁最多功能**的方向。当前 `settings` 同步层的设计
（查询键、乐观锁、白名单）已经为它留好了位置 —— 文档里明确写了
「把 `device_pk` 换成 `account_id`，客户端接口调用一行都不用改」。

需要新增：

| 表 | 作用 |
|---|---|
| `accounts` | 账号主体（手机号/邮箱/第三方 openid） |
| `account_devices` | 设备与账号的关联（一账号多设备） |
| `entitlements` | 会员 / 权益（配合付费） |
| `account_tokens` | 登录态（access / refresh） |

服务端改动：`/settings/*` 支持账号命名空间；新增 `/auth/*`（短信/邮箱验证码、
第三方 OAuth）；`/profile` 与 `/leaderboard` 从设备维度切到账号维度。

客户端改动：登录页 + 令牌存储 + 启动时静默续期。

解锁的能力：跨设备同步、换机无损、会员权益、可迁移的战绩。
风险：账号体系意味着**合规义务升级**（个人信息保护、注销通道、数据导出）。
做之前建议先把隐私政策与注销流程准备好。

### 3.2 对抗刷量（当前方案的边界）

现在的防线是「`app_key` 公开 + `app_secret` 签名 + 限流 + 单次增量上限」。
它挡得住脚本小子，**挡不住逆向客户端拿到 `app_secret` 的人**。
如果功德榜有了实际激励（比如兑换权益），必须加码：

| 手段 | 说明 | 成本 |
|---|---|---|
| 设备指纹 | 采集稳定的设备特征做去重 | 中，且**与当前隐私立场冲突**，需重新评估 |
| 行为特征校验 | 按上报节奏、累计值单调性、上线时长做异常打分 | 中，服务端加一张 `risk_scores` |
| 服务端侧熵校验 | 单设备日敲击超过物理上限（如 24h × 6.7 次/秒）直接不计入 | 低，**建议先做这个** |
| 人机验证 | 只在开启排行榜时触发一次 | 低，但要接第三方 |

**建议**：先做「物理上限校验 + 异常上报事件记录」，等真的被刷再加设备指纹。

### 3.3 消息推送 / 提醒

`announcements` 已支持版本区间与时间窗，但只能等客户端轮询
（`announcementPollMin` 默认 30 分钟）。

要做的事：桌面端可以用系统原生通知（Windows Toast / macOS UNUserNotification）
做「久坐提醒」「每日一签」这类本地推送 —— **不需要服务端**。
如果要做服务端主动推送，需要长连接或推送网关，成本陡增，暂不建议。

### 3.4 运营数据归档

`daily_active` 每天为每台活跃设备写一行；`event_log` 已限制 60 天。
按当前体量（几十台设备）完全无压力，但如果用户量上到万级：

- `daily_active` 需要按月分区或定期归档到 `daily_active_archive`；
- 看板趋势应改为读 `daily_stats`（已经是聚合表，没问题）；
- `event_log` 与 `crash_reports` 建议改为按需采样。

现在的设计（**不存敲击明细、只存聚合**）让这件事的成本天然很低，
这是当初刻意做的取舍。

## 4. 性能与容量边界（按这台机器实测）

| 资源 | 现状 | 结论 |
|---|---|---|
| 内存 | 总量 3.6G，可用约 0.9G | **不要再叠加大型服务**（Redis 已停用，别重启它） |
| 磁盘 | 60G 用 36G（60%），MySQL binlog 保留 3 天 | 够用，但别在本机编译 |
| 单次 `/taps` 的写库次数 | 约 6 次（设备、全局、每日、活跃、nonce、限流桶） | 批量上报后单设备约 0.2 req/s，十台设备不到 2 写/秒，**余量充足** |
| 理论承载 | 若 1000 台设备、每 5 秒一次批量上报 → 约 200 req/s | **超出这台机器能力**，届时要搬云函数或加机器 |

**扩展路径（按性价比排序）**：
1. 把限流与 nonce 从 MySQL 挪到 Redis（本机已装，只是被停用）——单机可再撑数倍；
2. `/taps` 改为写内存队列 + 异步批量落库；
3. 看板/统计类接口加 Cloudflare 缓存（现在 `public_cache=30` 秒，可放大到 300 秒）。

## 6. ✅ 已修复：`chr.cc` 的 DNSSEC 算法字段填错

**2026-09-23 已修复并验证通过。** 记录下来是因为：这类故障是**静默的**，
而且排查门槛高（要理解 DS / DNSKEY / Key Tag 的关系）。

### 故障现象

| 证据 | 修复前 | 修复后 |
|---|---|---|
| 注册局 DS | `2371 **8** 2 E4CDAA45…` | `2371 **13** 2 E4CDAA45…` |
| 权威 DNSKEY | `257 3 **13** mdsswUyr3DPW…` | 同左（未变） |
| 校验查询 `@1.1.1.1` | **SERVFAIL** | **NOERROR + `ad`** ✅ |
| 校验查询 `@8.8.8.8` | **SERVFAIL** | **NOERROR + `ad`** ✅ |
| 子域 `www` / `memo` / `ddz` | 全部 SERVFAIL | 全部 NOERROR ✅ |

**影响范围是整个域名的所有子域**，不是单个站点。

### 根因：只有「算法」字段错了

按 RFC 4034 用 Cloudflare 的 KSK 反算（算法字节参与 Key Tag 与摘要的计算）：

| 假定算法 | Key Tag | SHA-256 摘要 |
|---|---|---|
| **13（ECDSA P-256）** | **2371** ✅ 与 Cloudflare 一致 | **`E4CDAA45…8F3D13B3`** ✅ 与 Cloudflare 一致 |
| 8（RSA/SHA-256） | 2366 ❌ | `03832E5E44E9A03A…` ❌ 完全不同 |

同一个摘要不可能同时属于算法 8 和 13 —— 所以注册局里那条 DS 是
**把 Cloudflare 给的算法 13 数据误存成了算法 8**（摘要照抄，算法下拉框选错）。
「本机能打开、浏览器打不开」的差异就来自：本地解析器没做校验或走了缓存。

### 修复方式（域名所有者操作）

正确的 DS 五元组，以及注册商表单的对应填法：

```
chr.cc. 3600 IN DS  2371  13  2  E4CDAA45FCED0F0528D5060F993243CA4BFC27CD1BB7E396B1F682F88F3D13B3
                    │     │   │  └─ 摘要（保持原值）
                    │     │   └──── 摘要类型 = SHA-256 (type 2)
                    │     └──────── 算法 = ECDSA Curve P-256 with SHA-256（算法 13）★ 唯一要改的
                    └────────────── Key Tag = 2371
```

| 表单字段 | 填什么 |
|---|---|
| 密钥标签 Key Tag | `2371` |
| **加密算法 Algorithm** | **ECDSA Curve P-256 with SHA-256**（可能写作 `ECDSA P-256`、`EC P-256/SHA-256`、`算法 13`） |
| 摘要类型 Digest Type | `SHA-256` |
| 摘要 Digest | `E4CDAA45FCED0F0528D5060F993243CA4BFC27CD1BB7E396B1F682F88F3D13B3` |

**踩到的额外坑**：注册商的校验规则是「修改同一关键标签的 DS 时，摘要内容必须不同」。
本次摘要不变，所以「修改」会被拒 —— 实际做法是**先删除旧 DS 行，再新增一条**。

**如果注册商的算法下拉里没有 ECDSA / 算法 13**，只有两条路：
1. 删掉 DS（DNSSEC 关闭，站点立刻恢复可访问，只是失去防篡改）；
2. 把 DNS 解析迁到支持算法 13 的服务商/注册商。

### 防复发：把巡检挂上

`Scripts/check_dnssec.py` 会批量体检域名的 DNSSEC，并在 DS 与 DNSKEY
不匹配时直接算出「正确的 DS 应该是多少」：

```bash
python Scripts/check_dnssec.py              # 默认清单：chr.cc / s2ss.com / wktyl.com / vogov.cn / xianyan.cc / iqg.cc / wyi.cc
python Scripts/check_dnssec.py --strict     # 有问题时非 0 退出，可挂监控
```

**结论（2026-09-23 巡检）**：`chr.cc` 正常；其余 6 个域名**均未启用 DNSSEC**，
解析状态全部正常。是否需要开启见下节判断依据。

### 其他域名要不要开 DNSSEC？

**先看结论：这台服务器上的其他 6 个域名目前都没开，解析都正常，可以维持现状。**

DNSSEC 的定位是「给 DNS 应答加数字签名」，让递归解析器能验证
**这条记录真的来自该域名、且途中没被篡改**。它与 HTTPS 是两回事：
HTTPS 保护的是拿到 IP 之后的传输，DNSSEC 保护的是「拿到正确 IP」这一步。

| 维度 | 开启后 | 说明 |
|---|---|---|
| 防 DNS 缓存投毒 / 中间人改解析 | ✅ 有效 | 这是它唯一的、也是真实的价值 |
| 防域名劫持（改 NS 指向） | ✅ 部分有效 | 需要注册商侧也支持锁定 |
| 查询内容保密 | ❌ 无 | 不加密，仍是明文（要保密得用 DoH/DoT） |
| 解析速度 | ❌ 略慢 | 报文更大、多一次验签；通常无感 |
| 抗 DDoS | ❌ 无 | 反而多一个可被利用的失败点 |
| SEO / 排名 | ❌ 无 | Google 不把它当排名因子 |
| **配置错误的风险** | ⚠️ **高** | 配错会让**整个域名所有子域无法解析**（本次实例） |

**建议开启的场景**：
- 有用户账号 / 登录 / 支付体系的站点（解析被劫持的后果最严重）；
- 有合规或投标要求（部分等级保护、金融行业规范会点名）；
- 品牌被仿冒风险高、曾经遭遇过解析劫持的域名。

**建议暂不开的场景**：
- 纯展示站、个人工具站、内部测试域名；
- DNS 由不熟悉 DNSSEC 的人手工维护（配错比不开更糟）；
- 后续还要频繁更换 DNS 服务商的域名（换服务商要重新对齐 DS）。

**如果决定开，请务必按这个顺序做**：
1. 先在 Cloudflare（DNS 侧）启用 DNSSEC，拿到它给出的 DS；
2. 到注册商处**新增**该 DS（**算法下拉要选 Cloudflare 给出的那个**，别凭印象选）；
3. **立刻用 `dig +dnssec <域名> @1.1.1.1` 验证出现 `ad` 标志**，
   再用 `python Scripts/check_dnssec.py <域名>` 复核；
4. 把 `check_dnssec.py --strict` 挂进定时任务 —— 密钥轮换、换 DNS 服务商、
   注册商侧改动都可能让 DS 与实际密钥失配，而这个故障是静默的。

|---|---|---|
| 匿名统计默认开启 | `AppSettings.telemetryEnabled` 默认 `true` | v2 后端下线时默认关，v3 上线后看板数据源全靠它 —— 默认关等于看板永远不动 |
| 空闲后首次敲击立即上报 | 三条触发线 + `tapMinIntervalMs` 下限 | 原来要攒够 20 次或等 5 秒，用户敲一下看不到任何反馈 |
| `/taps` 409 自愈 | 补一次 `/launch` 再重试（只补一次） | 启动上报偶发失败 → 整场敲击被静默丢弃，且无任何提示 |
| 上报失败自动重试 | 最多 3 次，间隔同攒报间隔 | 用户敲完最后一下就停手时，最后一批会一直躺在内存里 |
| 看板整页刷新 | `/stats/overview` + 前端重绘 | 原来只有数字卡会刷新，趋势图/表格/榜单永远停在首次渲染 |
| 最后更新时间 + 脉冲 + 暂停 | 前端 `live-bar` | 「刷新了但没变化」和「根本没刷新」看起来一样，需要有可见反馈 |
| 客户端「上报状态」页 | 设备 ID、最近上报结果、全网数字 | 敲击是 fire-and-forget，此前**没有任何地方**能回答"我的数据上去没有" |
| 功德榜页面 | 周/月/总榜 + 参与开关 + 昵称 | 唯一能让人主动打开 App 的社交功能 |
| 每日一签 | 设置菜单顶部 | 仪式感，且文案后台随时可改 |

### 7.2 还值得做（按性价比排序）

| 优先级 | 项 | 服务端 | 客户端 | 价值 |
|---|---|---|---|---|
| **高** | **敲击浮层回显全网今日** | 已下发 `global.taps_today` | 在 MeritToast 上加一行小字 | 每一下敲击都在说"数据上去了"，是"敲了没反应"的终极解法 |
| **高** | **里程碑达成提示** | `Rank::titleFor` 已返回 `next_at` / `progress` | 跨过阈值时弹一次 | 把"敲 100 次才 1 功德"的枯燥感变成有目标的反馈 |
| 中 | **看板改用 SSE 推送** | 新增 `/stats/stream` 长连接 | 已有渲染逻辑，换数据源即可 | 秒级实时；代价是长连接占用，这台 4G 机器要评估 |
| 中 | **看板加"我的设备"视图** | 无（`/profile` 已支持） | 输入设备 ID 看自己的名次 | 让用户能验证"我确实在榜单里" |
| 中 | **在线人数实时曲线** | 需要 `online_samples` 采样表 | 折线图 | 比"当前在线"更有表现力 |
| 中 | **敲击音效/皮肤在线市场** | `asset_packages` 已有表 | 下载 + SHA-256 校验 | 内容生态 + 未来的付费点 |
| 低 | **小时级热力图** | `hourly_stats` | 本地按小时聚合 | 好看，但要等写入量稳定 |
| 低 | **久坐提醒（本地通知）** | 无（纯本地） | 平台通道 | 桌面端不需要服务端，成本可控 |

### 7.3 两条已经踩过、别再踩的坑

1. **"看板不动"极少是接口坏了**。这次线上 `global_stats.taps` 长期为 0，
   但接口是通的 —— 问题在客户端默认不上报。排查顺序应当是：
   **客户端开关 → 上报是否发出 → 服务端是否收到 → 看板是否刷新**。
   `test_dashboard_live.py` 就是把这条链路一次性跑完的脚本。
2. **"刷新了但没变化"必须给出可见反馈**。纯数字轮询在数据量小时
   与"页面卡死"无法区分，所以加了最后更新时间、脉冲与暂停按钮。

## 8. 明确的「不做」

- **不存敲击明细**。原始序列留在客户端，服务端只保留聚合口径 ——
  既是性能选择，也是隐私立场（避免形成可关联的行为轨迹）。
- **不做设备指纹**（除非被真实刷量倒逼）。与「匿名统计」的定位冲突。
- **不在本机编译任何东西**；不重启 Redis；不动 443（站长已明确不处理证书）。
- **不自行修改 `chr.cc` 的 DNS / DNSSEC** —— 必须域名所有者操作（见第 6 节）。
